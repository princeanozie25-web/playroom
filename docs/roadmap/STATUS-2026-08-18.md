# Playroom Status — 18 Aug 2026

## 1. Headline

Playroom's foundation is real and unusually well-tested: P0 and the P1 core ship with adversarial CI, and the two load-bearing safety stages that exist — context isolation and deny-by-default mandate evaluation — are enforced structurally, not by convention. But the fabric is one-and-a-half of four stages: **mandates are unsigned, there is no receipt/hash-chain audit, no inbound screening service, and no egress DLP.** Meanwhile the project has out-built its own roadmap in one direction — a governed HTTP "action door" (SCC/S21) already lets an external Claude Code on a machine we don't control act in a room under a permit at zero inference cost to Playroom — which is exactly the economic shape the new subscription-via-MCP north star wants, just over REST+Bearer instead of MCP+OAuth.

## 3. The trust fabric (the moat)

Of four stages plus the audit chain, **one is solid**. The README quietly redraws "the fabric" as identity/context/mandate/receipt — substituting context-assembly and receipt for the Bible's screening and egress — which is itself the honest tell that two stages don't exist.

| Stage                               | State                                 | Enforcing files / why                                                                                                                                                                                                                                                                                                                                                                 |
| ----------------------------------- | ------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **1 — Identity stamping**           | **Partial**                           | `apps/api/src/stamp.ts` derives `{member_id, principal_id, mandate_hash}` from DB rows and throws `UnstampableMemberError`; the wire has no `author` field (`protocol.ts`), so the spoof is unexpressible. **But** the §8.1 stamp-_or-drop_ half is unenforced (single gateway, "nothing to drop yet") and identity is a bearer credential — a process, not an Ed25519-signed person. |

## 4. What de-gating changes

Dropping the revenue gate removes the _artificial_ blockers, not the _technical_ ones. What actually reprioritizes:

- **S2.9 (Stripe) is cleanly gone** — nothing to unwind (zero billing code ever written). Note: the Bible §68 had _restored_ this commitment, so the owner's drop reverses a documented decision — **worth a one-line ADR** to close the loop.
- **P4 is no longer gated on "a paying pilot renewed."** Previously P4 needed _P2 exit + paying pilot + platform-policy ADR_. The pilot clause is dead. **What still gates P4 is real work, not revenue:** the P2 exit bar (receipts/chain, screening-L2, egress-DLP, bridge) and the unwritten **ADR-007** platform-policy review. De-gating does _not_ make P4 buildable today — it makes the _sequence_ the only constraint.
- **The autonomy stack (S-LOOP/DIAL/TASK/PUSH/SCC) loses its "wait for revenue" hold.** These beyond-roadmap slices were already live on Fly; with no revenue gate, continuing to harden and productize them is now the unambiguous main line rather than a side quest.
- **Net effect:** priority shifts from "prove willingness to pay" to "close the fabric gaps that make the SCC/subscription path _safe to open to a non-Prince user_" — signed mandates, receipts, and the egress sweep are now the critical path, because they're the conditions that currently keep RT-005 / S04-N2 / UI3-N1 "survivable only because nothing external happens yet."

## 5. The MCP / subscription goal

**Where we are:** the _hard_ part is done. An external Claude Code already pulls history, works, posts, requests `pr.merge` → gets `CO_SIGN` → **stops**, and cannot self-sign; Prince signs, the agent polls the resolution (2ba48f5, e00a05e). Inference runs on the external agent — **zero cost to Playroom**, which is precisely subscription economics.

**The concrete gap** — today it runs over the _wrong transport and auth shape_:

- Transport is plain Fastify REST (`POST /rooms/:id/actions|messages|interrupts`, `server.ts`), **not MCP**.
- Auth is a custodial `prm_` bearer token minted at `/redeem` (`credentials.ts`), **not per-user OAuth**.
- It's driven by a Claude Code _CLI on Prince's own machine_, **not a Claude subscription client speaking MCP**.
- No `packages/hosts/` seam exists yet (the Bible's designated home for the connector).

**Recommended sequence to "drive a Playroom room from a Claude subscription via MCP"** — each builds on what exists:

1. **ADR-007** — the platform-policy review. It's the named gate and it's unwritten; write it first so the rest is scheduled, not speculative.
2. **S4.2 — remote MCP server** in a new `packages/hosts/` seam, wrapping the _existing_ command layer as tools (`list_rooms`, `read_room`, `post_message`, `list_pending_tags`, `respond_to_decision`, `get_receipt`). Per ADR-004/RA-001 this is **"an adapter over commands, zero new business logic"** — the REST door already proves every one of these operations works. **Lowest-risk, highest-leverage step.**
3. **S4.1 — OAuth 2.0 (auth-code + PKCE, per-user tokens, principal binding, revocation)** replacing the `/redeem` bearer credential. This is what turns "a custodial seat token" into "_my_ subscription identity." Bigger lift; it's the real auth-shape change.
4. **S4.3 — pending-tag surfacing + notification** for connected members (they aren't summonable by tag; tags surface as pollable pending items). **The notify half already ships** (S-PUSH, observed on Prince's phone); build the `list_pending_tags` queue half.
5. **S4.4 — MCP sampling** — _later, and externally blocked_ on first-party client support. Until then the connected agent's model runs inside the user's own Claude app on their plan, which **is** the goal; sampling is only the further upgrade.

Do **not** count `packet-tracer-mcp/` as progress — it's an unrelated Cisco project, deliberately excluded from Playroom's images (35b0abd).

## 6. Recommended next slices (ordered)

1. **Write ADR-007** (platform-policy) and a short ADR recording the revenue-gate drop / S2.9 supersession. Cheap, unblocks scheduling P4, closes a documented reversal.
2. **S2.1 signatures — sign the mandates.** The single most load-bearing shortfall: authority is asserted by a git-committed JSON file, not a key. This is the precondition for opening _any_ door to a non-Prince holder (closes S04-N2). The `!sig_valid()` branch already exists waiting for a check.
3. **S4.2 remote MCP server** over the existing command layer (`packages/hosts/`). Directly serves the new north star, near-zero business-logic risk, and immediately usable with the current bearer auth before OAuth lands.
4. **S2.3 receipts + hash chain + daily root.** The moat's missing tamper-evidence and the prerequisite for S3.5's verification page; a headline P2 deliverable currently at zero.
5. **S2.5 egress sweep + canary seeding** _before_ the first non-Prince credential exists (UI3-N1's explicit trigger). Two credential leaks were already found by accident in prod; the systematic sweep is still open.
6. **S4.1 OAuth per-user**, then **S4.3 pending-tag queue** — the remaining two pieces that convert the proven SCC door from "custodial REST" into the actual subscription-MCP shape.

Carried honestly: S2.6 GitHub bridge, S3.x (A2A/reputation/email/orgs), and S4.4 sampling remain **not-started** or externally blocked, and the S1.X / S2.X phase-exit clips (in-room PR clip; 20 PRs + verifying chain) are **unmet** — the qualitative heart is demonstrated, the quantitative and cryptographic bars are not.
